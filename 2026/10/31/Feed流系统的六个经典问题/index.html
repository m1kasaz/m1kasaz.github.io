Feed流系统的六个经典问题

发表于2026-10-31|更新于2026-10-31|系统设计
|总字数:1.7k|阅读时长:6分钟|浏览量:

Feed 流系统的架构与六个经典问题。

存在的问题：

  1. 深分页问题

    现象：用户一次feed流拉了500多页数据，redis放不下只能去DB里查，这时候MySQL要执行耗时很长的命令

    出现的问题：

    1. 用户层面：数据很慢，或者根本拿不到数据
    2. C端：超时重试，一直占着连接池，资源被浪费
    3. Server侧：同C端
    4. DB侧：进行无意义的回表，整个磁盘IO队列阻塞

    深度分页介绍及优化建议

    解决办法：

    1. 禁止深度分页，C端直接设置最大分页数，超过这个分页数禁止请求

    2. 建立游标，每次请求结束都带着一个NextID，用于直接跳到下一页的开始

  2. 看到旧/重复视频

    现象：用户漏/重复看视频

    插入一行，OFFSET 20 指向的内容就从 v20 变成 v19，重复和漏看是同一个 bug 的两面。

    本质是通过分页参数控制查询时，如果数据有增删，就会对后续的查询造成影响

    解决办法：

    1. 基于时间过滤掉旧的数据，在本地进行视频去重
    2. 加入游标，不需要关注数据变化，直接从下一条开始取数

  3. 缓存穿透

    现象：某个大V的Key有几百万个用户一直访问，但是这个大V的Key突然过期了，几十上百万流量直接打DB，导致数据库崩溃

    解决办法：

    1. 热Key永不过期：热点Key不设置过期时间，靠定时任务更新缓存

    2. 逻辑过期：设置一个时间戳，每次访问Key的时候顺便对比一下，如果过期了就重新拉一次缓存

  4. 大Key问题

    现象：关注 5000 个 UP 主的深度用户，收件箱攒了上亿条记录，Redis 内存占用居高不下，运维被迫频繁扩容。

    大Key的定义：

    数据结构 判定阈值建议
    String 单个 value 内存占用 > 10 KB（更严格的标准为 > 50 KB）
    Hash / Set / ZSet / List 元素数量 > 5,000 个，或总内存占用 > 10 MB

    基于命令的分析方法：

    • redis-cli --bigkeys
      • 原理：底层通过 SCAN 命令渐进式遍历所有 key，不会阻塞主线程。
      • 局限：它只按数据类型各汇报一个最大 key（例如仅输出“最大的 String 是哪个，最大的 List 是哪个”），且针对容器类型（Hash/Set/ZSet/List）统计的是元素数量而非实际字节大小，无法列出所有超标的大 key。
    • redis-cli --memkeys（Redis 6.0+）
      • 原理：同样通过 SCAN 遍历，但通过 MEMORY USAGE 对比实际物理内存占用。
      • 局限：同样只记录各类型的全局前几名，且对极大的 key 计算 MEMORY USAGE 时会有轻微性能开销。
    • MEMORY USAGE <key>（Redis 4.0+）
      • 原理：用于精准查看单个 key 所占用的内存字节数（采样估算或遍历）。

    自动化分析：

    • 离线解析 RDB 快照（最推荐、主流做法）
    • 云厂商托管 Redis（自带自动化能力）

    影响面：

    1. 阻塞单线程，引发服务级联超时
    2. 网卡打满，单机的其他服务被拖垮
    3. 从库因传输超时断开与主库的连接，主从失效

    解决办法：

    1. 单个用户设置桶上限，超出上限部分通过DB读取

    2. 设置Key过期时间，定期删除桶消息

  5. 推/拉模式

    现象：一个关注 800 人的普通用户，每次下拉刷新 feed 要 3 秒，接口 P99 全线飘红。

    解决办法：

    1. 查询归并

    2. 加一层缓存，结合推模式

    3. 小作者推

  6. fanout推同步阻塞结果

    现象：千万粉 UP 主点下「发布」，页面转圈 30 秒后报超时；视频其实已经入库，但粉丝几小时后才在 feed 里看到。
